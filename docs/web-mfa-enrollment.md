# إعداد Authenticator من بوابات الويب

## تجربة الهاتف

زر التفعيل يفتح خطوتين داخل بطاقة الأمان، بألوان الوضع النهاري والليلي:

1. إضافة الحساب: رابط لفتح تطبيق مصادقة متوافق، أو QR، أو اسم الحساب ومفتاح يدوي مع نسخ. البدائل تظهر عند اختيارها، وتستخدم المفتاح نفسه.
2. إدخال رمز التطبيق من 6 أرقام وتأكيده. الإدخال يدعم اللصق والرموز المنسوخة بمسافات، ولا يُرسل تلقائيًا عند الانتقال إلى تطبيق آخر.

بعد نجاح التأكيد تظهر رموز الاسترداد مع النسخ والتنزيل، ثم «حفظت الرموز — إنهاء». إنهاء العرض لا يوقف الحماية. فتح التطبيق يعتمد على دعم الجهاز والتطبيق لبروتوكول `otpauth`؛ لا يستطيع الموقع قراءة رمز التطبيق تلقائيًا. يبقى QR والمفتاح اليدوي بديلين.

يُنشأ QR داخل الخادم باستخدام [node-qrcode](https://github.com/soldair/node-qrcode)، ثم يُعاد كصورة PNG مضمّنة. لا يُرسل المفتاح إلى موقع خارجي لتوليد QR. صيغة الرابط تتبع [Key URI Format](https://github.com/google/google-authenticator/wiki/Key-Uri-Format).

## حالة الإعداد والأمان

- يحتفظ `webMfaEnrollmentService` بالإعداد في جلسة الويب مشفّرًا بواسطة AES-GCM، مربوطًا بمعرّف الحساب ونوعه. الإعداد صالح 10 دقائق، وإعادته خلال المدة لا تولد حسابًا جديدًا في التطبيق.
- لا يُخزَّن المفتاح أو رموز الاسترداد في localStorage أو sessionStorage. تُفرغ بيانات العرض عند مغادرة الصفحة، ويستعيد طلب الحالة البيانات المتاحة عند العودة.
- التأكيد يستخدم المفتاح ورموز الاسترداد المحفوظة في الجلسة، وليس قيمًا يختارها العميل في جسم الطلب. رمز خاطئ أو إعداد منتهي لا يفعّل الحماية.
- الحساب المفعّل بالفعل لا يبدأ إعدادًا جديدًا عبر هذا المسار؛ يلزم إيقاف الحماية من إدارتها أولًا.
- بعد التأكيد يمسح الإعداد المؤقت المفتاح ورابطه، ويحتفظ برموز الاسترداد مشفّرة لمدة إتاحة 15 دقيقة حتى تأكيد الحفظ. تربط بصمة العامل هذه الرموز بالحماية التي أُنشئت لها، ولا تُعرض لعامل تغيّر لاحقًا.
- الحماية الدائمة تستعمل خدمة MFA الموجودة: مفتاح مشفّر ورموز استرداد محفوظة كبصمات. الإقرار بحفظ الرموز يمحو العرض المؤقت؛ لا يغير تفعيل العامل.
- استجابات `/security/mfa` تحمل `Cache-Control: private, no-store` وتخضع لسياق الحساب وCSRF الحاليين. لم تتغير مسارات تطبيق الهاتف عبر JWT.

## مسارات الويب

| الطلب | السلوك |
|---|---|
| `GET /security/mfa/status` | حالة الحماية، والإعداد أو رموز الاسترداد المؤقتة للحساب الحالي إن كانت متاحة |
| `POST /security/mfa/setup` | إنشاء / استئناف إعداد، يتضمن رابط التطبيق وصورة QR والمفتاح |
| `POST /security/mfa/confirm` | تأكيد `token` مقابل إعداد الجلسة؛ تبقى أجسام العملاء الأقدم مقبولة لكن القيم الإضافية لا تستبدل إعداد الخادم |
| `POST /security/mfa/setup/cancel` | إلغاء الإعداد غير المؤكد فقط |
| `POST /security/mfa/recovery/ack` | تأكيد حفظ رموز الاسترداد وإزالة نسختها المؤقتة |

## التحقق

```powershell
npx jest tests/webMfaEnrollment.test.js tests/accountMfaService.test.js tests/mfaService.test.js tests/executorSettingsMobile.test.js --runInBand
node scripts/checkMfaEnrollmentBrowser.js
node scripts/checkMfaEnrollmentBrowser.js --company
```

فحص المتصفح مقيد بخادم `http://127.0.0.1:4577` وقاعدة `ahram_company_mobile_demo_v2` المحلية، ويحتاج `MONGO_URI` و`PUPPETEER_EXECUTABLE_PATH`. ينشئ حساب وكيل تجريبيًا مستقلًا افتراضيًا، أو شركة ومالكها عند تمرير `--company`، ثم يحذف حساباته وأجهزة وثوقها عند الانتهاء. يختبر الخادم الفعلي: QR، رابط التطبيق، المفتاح اليدوي، استئناف الإعداد بعد تحميل جديد، رفض الرمز الخاطئ، قبول TOTP صحيح، استئناف رموز الاسترداد ونسخها وبيانات تنزيلها، الإنهاء، والإيقاف برمز صحيح. يفحص عرضي النهار والليل بعروض 320 و390 و430.

لا يفتح الفحص تطبيقًا خارجيًا على الجهاز، ولا يعدّل MFA لحساب المستخدم. يتم التقاط بيانات النسخ والتنزيل داخل سياق الاختبار دون تغيير حافظة النظام أو حفظ رموز الاسترداد في ملفات فعلية.

تتطلب الإضافة الجديدة تثبيت الاعتماديات بواسطة `npm ci` عند النشر.

نجحت الاختبارات المركّزة ومسارا المتصفح الفعلي للشركة والوكيل. محاولة فحص البوابات الأوسع تعذرت في هذه البيئة عند تشغيل MongoDB المؤقت (`spawn UNKNOWN` / مهلة بدء MongoMemoryServer)، ولم تُعامل كنجاح أو تُرفع مهلها لإخفاء المشكلة. ظل الخادم المحلي بقاعدة MongoDB الفعلية يعمل واجتاز مسار الإعداد الكامل.
