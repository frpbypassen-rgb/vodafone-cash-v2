# Controlled restart with one preserved provider hold

Explicit operator authorization is required to restart while leaving the known unresolved transaction unchanged. The tool defaults to read-only preflight; `-Apply` enters a brief maintenance window. This is not a financial resolution tool.

Startup readiness uses a six-minute wall-clock deadline by default (`-ReadyTimeoutSeconds`, range 60–900), with periodic progress output. The server has been observed taking approximately four minutes on cold startup; the former ninety-second loop could expire while a valid process was still initializing. This extends waiting only; no readiness, fingerprint or financial admission checks are bypassed.

On a busy live site, Apply first takes a protected-document-only snapshot (`--snapshot-only`), verifies process ownership and closes admission. Only then does it require full empty-work inspections. The snapshot-only flag cannot be combined with an expected fingerprint and is never used for the drain barriers or final readiness. This avoids requiring an idle gap before admission is closed. Read-only preflight without Apply still checks all work normally.

Explicit `-PreserveManual` permits idle persisted `pending`/`accepted` rows while keeping every inspected queue empty. Financial schedulers must already be explicitly off and remain unchanged. After admission closes, the first drain barrier captures up to fifty rows: pending unassigned rows, or pending/accepted rows belonging to a group with explicit `isApiBot=false`, without original API routing, review, dispatch markers/results or automatic-completion flags. API work, unknown executor types and `processing` rows remain forbidden. Every complete document is fingerprinted; following barriers allow only those exact rows and reject new open work or any document change. The tool performs no database writes and never refunds or resends a preserved row. Pending/accepted manual work can continue through normal operator actions after the site reopens. This mode is not evidence of provider payment or permission to ignore executing work.

If the protected row has already become `completed`, `rejected`, or `cancelled_by_admin` through existing operations, `-AllowSettled` explicitly permits that existing terminal state and an empty active-work inspection. The complete row must still exist and retain its fingerprint across the transition; no state is changed or restored by the tool. It also continues to accept the original unresolved hold. New open work, incomplete inspection, missing rows, changed fingerprints and nonterminal replacement states still refuse the transition. An empty active-work sample alone does not prove payment success.

After admission closes, each of the two drain barriers can retry busy work up to twelve times, five seconds apart. Busy transaction diagnostics expose only counts/statuses; incomplete inspections and protected-document changes fail immediately. No operation is force-completed, canceled, re-sent or refunded to drain. Some work may require a client/provider callback blocked by maintenance; the bounded wait then refuses and restores the still-running old instance rather than waiting indefinitely.

`checkHeldRuntimeRestart.cjs` reads MongoDB with the native driver and the existing Redis queue inspector. It never imports the application, starts workers, calls a provider, retries jobs, or writes transaction/ledger records. It requires exactly the authorized `processing` row with `pending_reference`, `providerResultUnresolved=true`, a dispatch timestamp and no pending automatic completion. All other open transactions and all five inspected queues must be absent/empty. Missing or incomplete inspection fails closed. A SHA-256 fingerprint of the full document is compared without printing its contents.

`restartManagedRuntimePreservingHold.ps1` verifies the managed PID, script, directory, and unchanged tracked financial dispatch guards. Apply requires an elevated Windows shell, stops the known IIS site and blocks direct inbound TCP 3000, then repeats the hold/work checks. It stops only the verified managed instance; if PM2 leaves that exact same container alive, it verifies PID, creation time and port ownership before terminating it. It never kills the daemon or all Node processes, and it never overlaps two application instances. The new process must be healthy, use the same runtime worker switches, preserve the document fingerprint, and serve the new no-store login asset policy before traffic reopens. It saves PM2 only after success.

If the old instance remains alive after a pre-stop failure, traffic is restored to it. If it has stopped and validation fails, maintenance remains in place and the rule name is reported. Do not remove the rule or open the site until readiness and hold state have been reviewed. No financial state is forcibly restored if it legitimately changes: the script refuses the transition instead.

Tests cover held-document immutability, changed-state refusal, incomplete and busy queues, and the existing send/refund guards. PowerShell preflight success/refusal are exercised with mocked OS/database commands under Windows PowerShell; script parsing is checked. These do not emulate live IIS/ARR/firewall traffic or claim to guarantee provider availability. Stop admissions and maintain normal provider reconciliation procedures; a preserved hold does not prove whether a provider paid.
