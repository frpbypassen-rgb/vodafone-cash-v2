# خطة استقرار الإنتاج والانتقال مع استمرار الخدمة

تاريخ الإعداد: 2026-10-27. ثبت بالفحص أن البروكسي IIS/ARR تحت Plesk على Windows.

## النطاق وحالة التنفيذ

الهدف إصلاح تعارض العمليات والمنفذ 3000، وصيغة عنوان IP، وتحذيرات Mongoose، وتشخيص رفض توكنات الهاتف، مع الحفاظ على التحويلات والجلسات والإيصالات.

هذه خطة مستقلة؛ لا تستبدل مهام بوابة الشركات في `tasks/`. التنفيذ المحلي لا يعني النشر على الإنتاج. الخادم الحي بعيد، ولا يملك هذا السياق وصولًا مباشرًا إلى إدارته. لا تُنفّذ أوامر إيقاف أو إعادة تشغيل أو تعديل بروكسي أو قاعدة إنتاج قبل الحصول على جرد الخادم وتحديد النسخة الخادمة.

**الحالة الحالية:** نجح الإقلاع الخاص على خادم الإنتاج عند 23:25 بتوقيت ليبيا: PID 8808 على المنفذ المحلي 62149، بوضع probe، مع اتصال DB/Redis/الجلسات وحجب مسارات العمليات وSocket.IO وتخطي التهيئة الخلفية. أُغلقت عملية الاختبار وحدها وبقيت الخدمة الفعلية جاهزة على PID 6764. لم يُغيّر IIS أو PM2 أو يُنقل المرور العام.

اختار المستخدم الإبقاء على شرط عدم الانقطاع وتأجيل النقل إلى حين التحقق من روابط API المستخدمة. كما اختار تجاوز المراجعة الإضافية بنموذج آخر. أثبت فحص خارجي أن `ahrampay.com:3000` وعنوان الخادم المباشر يصلان إلى العملية الفعلية نفسها؛ وجود هذه الوجهة لا يثبت أن الشركات تستخدمها، لكنه يمنع افتراض مرور كل الطلبات عبر IIS. قرار التشغيل المتوازي الكامل سُحب بعد مراجعة العمال، وتفاصيل الموانع في [مراجعة تسليم التشغيل](runtime-handoff-review.md).

الخطوة الحالية قراءة إعدادات الربط وجمع إثباتات عناوين العملاء فقط. لا يُشغّل المرشح بدور full ولا يُغلق المنفذ 3000 أو تُوقف العملية الفعلية قبل حسم طريقة الوصول وتسليم العمال. أداة [قائمة مراجعة الروابط](api-routing-verification.md) لا تشغل التطبيق ولا تغير إعدادات الحسابات أو المفاتيح.

## أدلة التشخيص

- السجل المرسل أظهر `EADDRINUSE` واختلاف PID في PM2 عن مستمع 3000. هذه الأرقام تاريخية ولا يجوز استخدامها لاحقًا كأهداف للإيقاف.
- تحذيرات Mongoose تتعلق بإرجاع المستند بعد التحديث، وبعضها من عملية قديمة.
- بعض طلبات الهاتف تصل بعنوان IPv4 مع منفذ وتُرفض مصادقة طلبات أخرى بـ401/403. لا يكفي ذلك لإثبات سبب رفض التوكن.

## نتيجة جرد الإنتاج عند 20:23 UTC

موقع `ahrampay.com` يستخدم القاعدة `ReverseProxyInboundRule1` إلى `http://localhost:3000`، ودليل IIS هو `C:\Inetpub\vhosts\ahrampay.com\httpdocs`. خدمات IIS وARR تعمل.

المستمع الفعلي كان PID 6764 وجاهزيته وMongoDB والجلسات وRedis سليمة. في المقابل عرض PM2 العملية `ahram-pay` برقم 2848، دون امتلاك المنفذ، وعدّاد إعادة تشغيل 451. كلاهما تابع للـdaemon نفسه (2820). هذه لقطة تاريخية وليست أرقامًا يجوز قتلها لاحقًا. المهمة المجدولة `AhramPay-PM2-Startup` موجودة، لكن تفاصيل أمر تشغيلها وملكية العمال لم تُحسم.

إصدار الخادم `ca995e84`، مع تعديلات محلية وخدمات عمولة API غير متتبعة ومجلد Git متداخل. يجب نقل هذه التعديلات إلى الإصدار المرشح ومراجعتها؛ لا يكفي نسخ الفرع وحده. لم يجر إيقاف أو إعادة تشغيل أو تعديل إعدادات هذا الخادم أثناء تنفيذ هذه الخطة.

## ما نُفّذ محليًا

- تطبيع مفتاح تحديد الطلبات فقط: إزالة منفذ IPv4 ودعم IPv6/subnet، دون تعديل عنوان الجهاز المستخدم للمصادقة أو قراءة XFF مباشرة.
- إعداد `TRUST_PROXY` قابل للتحديد الصريح؛ الافتراضي الحالي يبقى كما كان. لم يُغيّر إعداد الإنتاج.
- استبدال 66 خيارًا إنتاجيًا لـMongoose بـ`returnDocument: 'after'` في JavaScript وTypeScript، مع إبقاء المرشحات والجلسات وعمليات الخصم والمعاملات كما هي.
- تسجيل رموز رفض مصادقة الهاتف من قائمة ثابتة مع PID، دون تسجيل كلمات المرور والتوكنات. هذا تحسين تشخيص؛ سبب 401/403 الحالي لم يثبت بعد.
- وضع `RUNTIME_ROLE=probe` للفحص على loopback فقط: يقبل قراءة الجاهزية، ويرفض بقية المسارات وSocket.IO، ولا يبدأ العمال والمجدولات أو تهيئة البنية في مرحلة الإقلاع. لا يُوجّه إليه المستخدمون.
- `ecosystem.runtime-probe.config.js` يستخدم اسمًا ومنفذًا مستقلين، ويمتنع عن الإقلاع مع إصدار قديم لا يحتوي بوابة الفحص. لم يُشغّل على الإنتاج.
- `inspectProductionQueues.cjs` يقرأ أحجام مفاتيح BullMQ ثابتة فقط، وعينة محدودة بحد أقصى 101 من حالات العمليات عبر فهرس الحالة، ويتجاوز الاستعلام عند غياب الفهرس. لا يبدأ التطبيق أو العمال ولا يطبع بيانات الحسابات أو محتويات المهام. النتيجة لقطة وليست إذنًا بإيقاف عامل.

نجح اختبار إقلاع محلي فعلي بقاعدة اختبار منفصلة: جاهزية النسخة المعزولة، رفض مسارات العمليات والدخول بـ503 وSocket.IO بـ403، وصفر مستندات في مجموعات الحركات والسجل والتقارير المختبرة. نجحت فحوص TypeScript والاختبارات المخصصة؛ نتائج الفحص الشامل تُسجّل في تقرير التحقق المصاحب.

### قيد يمنع الانتقال المتسرع

تهيئة منتج BullMQ والعامل مترابطة حاليًا، وبعض مسارات API تتحقق من تفعيل العامل. لذلك لم يُضف وضع `web` ولم يُعطّل عامل النسخة الخادمة. يجب إثبات آلية إنتاج المهام وتسليم ملكية العمال، وفحص المهام الجارية والجلسات وWebSocket وطريقة الرجوع في بيئة اختبار قبل أي تغيير لتوجيه IIS. وضع `probe` لا يخدم المستخدمين ولا يثبت وحده إمكان انتقال بلا انقطاع.

### تحديث فحص الطوابير عند 22:44 بتوقيت ليبيا

أكد الفحص أن MongoDB المستهدفة replica set. جميع قوائم الانتظار والحالات النشطة والمؤجلة والأولوية التي قرأها الفحص في الطوابير الخمسة كانت صفرًا. أظهر استعلام الحالات عمليتين مفتوحتين: واحدة `accepted` وأخرى `deposit_pending`، دون اقتطاع للعينة. يستخدم الفحص ملف البيئة الحالي وبيئة سطر الأوامر؛ لم يُثبت تطابقهما الكامل مع البيئة المحملة داخل العملية الخادمة القديمة. لا يقرأ الفحص الطوابير داخل ذاكرة العملية أو كل أقفال إرسال المزود، ولا يتنبأ بوصول تحويل جديد؛ هذه النتيجة لا تسمح بقتل العملية الخادمة أو إعادة إرسال العمليتين.

الخطوة التالية هي `scripts/prepareRuntimeCandidate.ps1`: ينشئ نسخة Git مستقلة خارج المشروع الخادم، ويطبّق تعديلات العمولة المحلية عبر دمج ثلاثي، وينسخ الملفات الجديدة المعروفة وملف البيئة دون إظهاره. يرفض تغييرات التشغيل غير المعروفة أو تعارض الدمج أو الوجهات الموجودة أو مسارات reparse/junction، ويتحقق أن المصدر لم يتغير أثناء التجهيز. يثبّت الاعتماديات داخل النسخة الجديدة مع `--ignore-scripts`؛ لا يشغّل التطبيق أو PM2 أو IIS أو قواعد البيانات. غياب بناء حزمة أصلية نتيجة تعطيل lifecycle hooks سيُكتشف لاحقًا في الفحص الخاص، ولا يُعالج بتغيير `node_modules` الحية.

نجحت سبعة اختبارات تكامل لهذا الإجراء على Windows PowerShell 5 باستخدام مستودعات وملفات بيئة اصطناعية. نفّذ المستخدم التجهيز على الخادم بنجاح: النسخة المرشحة من `f587e44c` موجودة في مجلد مستقل ينتهي بـ`fe2f29052fd04cc9bef604522c60d2a0`، مع دمج الملفات الخمسة المعدلة ونسخ ملفات العمولة الجديدة الثلاثة وتثبيت الاعتماديات دون lifecycle hooks. أكد التقرير بقاء المصدر والعمليات دون تغيير. التشغيل الخاص للنسخة المرشحة والنقل العام مرحلتان منفصلتان لم تبدآ.

### فحص ما قبل الإقلاع

تبين من مصدر connect-mongo المثبت أن `autoRemove: 'native'` ينشئ فهرس TTL عند الإقلاع. عُدّل `config/sessionStore.js` ليستخدم `disabled` في وضع `probe` فقط، بينما يبقى وضع التشغيل العادي كما هو. نجح اختبار إقلاع محلي فعلي على قاعدة جديدة، ولم تظهر مجموعة جلسات أو مستندات مالية.

الأداة `scripts/checkRuntimeCandidate.cjs` لا تقلع التطبيق ولا تفتح اتصال MongoDB/Redis. تتحقق من الإصدار والملفات الأساسية وتطابق ملف البيئة مع المصدر، وتطبّق تعديل مخزن الجلسات داخل المرشح فقط بعد مطابقة محتواه مع Git blob معلوم. ترفض أي تعديل سابق غير متوقع لذلك الملف. تفحص bcrypt وcanvas عمليًا ببيانات اصطناعية صغيرة، وتحلل ملفات JavaScript المحلية دون تنفيذها، وتتحقق من حل الواردات ومن وجود استدعاءات عند تحميل الوحدة تستلزم المراجعة. تفحص سياسة الإنتاج دون عرض أسرار، وتقرأ جاهزية الخدمة الحالية عبر GET فقط. التحليل الساكن لا يثبت غياب جميع الآثار الجانبية في شجرة الواردات، ولا يجيز تشغيل العمال أو التحويل العام.

نجح 18 اختبارًا مخصصًا للتحقق السابق، وتحليل الشيفرة، وحماية تعديل الملف، وإعدادات الجلسات وأدوار التشغيل. يُنتظر تنفيذ الأداة على المرشح لتحديد مشكلات الاعتماديات أو سياسة الإنتاج قبل تشغيله.

وصل فحص المرشح: البيئة مطابقة للمصدر وتنجح سياسة الإنتاج، ومخزن الجلسات مصحح، وجميع الاعتماديات المختبرة جاهزة باستثناء `canvas` (`MODULE_NOT_FOUND`). بقي الخادم الفعلي PID 6764 جاهزًا. إشارة الوارد غير القابل للحل في ملف المنفذين كانت عند مسار `ReversalService` الذي يُحمّل من TypeScript؛ أُعيد إنتاجها محليًا لأن الفاحص لم يحاك تسجيل ts-node في التطبيق. صُحّح الفاحص ليحل ملفات `.ts` و`index.ts` دون تنفيذها، مع إبقاء الواردات المفقودة أو خارج وحدات التشغيل مرفوضة.

أضيف خيار `--repair-canvas` إلى الفاحص للنسخة المعزولة فقط. يتحقق من تطابق إصدار حزمة canvas وملفي الربط JavaScript في المصدر والمرشح، ومن عمل الحزمة الأصلية على Node الحالي، ثم ينسخ ملفات `.node` و`.dll` العادية إلى مسار المرشح بعد فحص جميع الوجهات. لا يستبدل ملفًا مختلفًا موجودًا ولا يكتب إلى المصدر أو ينفذ سكربتات npm؛ يتحقق من محتويات الملفات بعد النسخ ومن بقاء المصدر كما كان. إذا لم توجد حزمة مصدر عاملة أو اختلف الإصدار، يتوقف دون اللجوء إلى تثبيت داخل المشروع الحي.

نجح 20 اختبارًا مخصصًا بعد الزيادة. شمل اختبار Windows نقل ملفات canvas المبنية إلى مجلد اختبار مستقل وتوليد PNG عبر عملية Node جديدة، ثم رفض اختلاف الإصدار أو ملف ثنائي متعارض. لم يُنفذ إصلاح canvas على المرشح البعيد بعد، ولم يُقلع التطبيق.

وصل فحص 23:12 بتوقيت ليبيا: أُصلح canvas 3.2.3 بنسخ 45 ملفًا أصليًا مبنيًا إلى المرشح مع بقاء المصدر دون تغيير. أصبحت جميع الاعتماديات جاهزة، ونجحت سياسة الإنتاج، ولم تبق ملاحظات في مراجعة تحميل الوحدات. أكد الفحص استمرار جاهزية PID 6764، وأصبح المرشح مؤهلًا للخطوة الخاصة فقط؛ لم يُقلع بعد.

### اختبار إقلاع خاص محدود المدة

أُضيفت `scripts/runRuntimeCandidateProbe.cjs`. تتحقق من محتوى أداة preflight مقابل نسخة Git محددة، وتعيد فحص المرشح والخادم الحالي قبل الإقلاع. تنشئ عملية Node واحدة على منفذ loopback عشوائي متاح، دون PM2، وبوضع `probe` مع تعطيل العمال والمجدولات والإرسال الخارجي وتقارير البريد. لا ترسل طلبًا يشبه العملية قبل إثبات PID الطفل ودور probe وحجب التعديلات عبر الجاهزية. تختبر رفض أربعة مسارات وSocket.IO، وتتحقق من رسالة تخطي التهيئة الخلفية، ثم تغلق الطفل الذي أنشأته وحده وتقرأ جاهزية الخدمة الحية وPID مرة أخرى. تنتظر الجاهزية لمدة قصوى 60 ثانية، وتتعامل مع فشل الإقلاع والمقاطعة بتنظيف الطفل. لا تغير IIS ولا PM2، ولا تحذف بيانات أو تفحص تغير أعداد السجلات المالية أثناء استمرار عمل المستخدمين.

نجحت سبعة اختبارات للمشغل، ونجحت معه المجموعات المخصصة الأخرى بإجمالي 27 اختبارًا. شمل ذلك رفض PID أو دور غير مطابق قبل أي POST، ومنع الإقلاع عند تدهور الخادم الحالي أو فشل preflight، واحتواء خروج الطفل وانتهاء مهلة جاهزيته. نجح أيضًا إقلاع التطبيق الفعلي محليًا بوضع الإنتاج على replica set معزول وRedis محاكى لا يقبل إلا أوامر التهيئة المقروءة: صفر مجموعات Mongo منشأة، وأوامر Redis الوحيدة CLIENT وINFO، وحجب المسارات وSocket.IO، وإغلاق الطفل وبقاء الخدمة المحلية جاهزة. هذه أدلة اختبار محلية؛ نتيجة الإقلاع الخاص على خادم الإنتاج لم تصل بعد.
- الكود الحالي يربط HTTP قبل بدء العمال، ويحتوي مفاتيح منفصلة للعمال والمجدولات والويبهوكس.

- [ ] اختبار آلية التحويل الفعلية على بيئة معزولة؛ لا افتراض أن `iisreset` أو `pm2 restart` انتقال بلا انقطاع.
- [ ] تحويل الوجهة تدريجيًا إن دعمها التكوين، مع إبقاء العناوين العامة وروابط المزودين ثابتة.
- [ ] الإبقاء على النسخة القديمة لخدمة الطلبات والاتصالات القائمة حتى تصريفها.
- [ ] تسليم العمال والمجدولات مع فحص الأقفال والمهام الجارية ومنع تكرار الخصم والإرسال، ثم إيقاف القديمة تدريجيًا.

القبول: استمرارية الطلبات والجلسات، عدم تكرار أو فقدان العمل المالي، وتطابق وجهة الموقع مع الإصدار المقصود. التنفيذ يعتمد على نتيجة جرد الخادم؛ لا ضمان بانقطاع صفري باستخدام عملية fork واحدة وحدها.

### 5. المراقبة والرجوع

- [ ] مراقبة الجاهزية وتكرار إعادة التشغيل وEADDRINUSE و401/403 وزمن الطلبات والطوابير لمدة أولية 15–30 دقيقة.
- [ ] الرجوع بالتوجيه للإصدار السابق عند تجاوز مؤشرات الخطأ، مع تنسيق ملكية العمال.
- [ ] لا استعادة لقاعدة البيانات أو عكس معاملات صحيحة عند الرجوع بالكود.
- [ ] اعتماد إعداد الإقلاع وPM2 بعد ثبوت الاستقرار، وحفظ السجلات السابقة مع تمييز الوقت وPID.
